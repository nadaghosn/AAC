# How I Verified the Work

**Tests.** Ran the full pytest suite (`pytest -v`) repeatedly throughout the work — 45 tests, all passing, including a new test I added for a coverage gap found during the documentation audit (`test_patch_blank_title_returns_422_and_keeps_title`). Also confirmed the same suite passes in CI by pulling the actual latest GitHub Actions run (`gh run view`), not just trusting a green checkmark from memory.

**Diff review.** Before applying any code or documentation change, reviewed the exact diff first — docstring additions to `app/main.py`/`app/storage.py`/`app/models.py`, the Dockerfile comment pass, and the full README rewrite were all shown as diffs for approval before being applied. Separately, reviewed the entire `final-project` branch diff against `main` for correctness, test coverage, Docker/CI safety, and scope creep, which surfaced concrete issues (a self-contradicting test count in the README, an internal `[VERIFY]` note leaking into the public Swagger docs, and ~20 scratch files sitting outside `docs/`).

**Docker.** Built the image (`docker build -t task-tracker:dev .`) and ran the container (`docker run -d --name task-tracker-dev -p 8000:8000 task-tracker:dev`) multiple times across the work, each time confirming: the container runs as the non-root `app` user (`docker exec ... whoami`), no secrets/`.git`/`.env`/`__pycache__` end up baked into the image (`docker run --rm ... find /app ...`), and the container reaches a healthy state.

**`/health`.** Hit `GET /health` directly after every relevant change — via `TestClient` for quick in-process checks, via a freshly started local `uvicorn app.main:app --reload --port 8000` process for the release baseline, and via `curl` against the running Docker container — confirming `200` and the expected `{"status": "ok", "timestamp": "..."}` body each time, rather than assuming it still worked.

**Manual scan.** Beyond automated tests, manually audited documentation claims against live runtime behavior (dumping `/openapi.json`, exercising edge cases like `PATCH` with `tags: null` through `TestClient`) to catch mismatches tests wouldn't surface; manually inspected `frontend/index.html` to confirm the Kanban board and create/edit modal markup were still intact; and manually checked `.github/workflows/ci.yml` line by line for shortcuts that could hide a real failure (`continue-on-error`, `|| true`, a skipped test step, a vague Python version, or a missing dependency-install step).
